# kafka-sales-etl — потоковый ETL-пайплайн продаж на Apache Kafka

проект: события о продажах поступают в Kafka, стрим-процессор чистит их,
дедуплицирует, обогащает и в реальном времени агрегирует в витрину «выручка по
категориям в минутных окнах», которая складывается в SQLite.

Стек: **Python, kafka-python, Docker Compose, SQLite, unittest**.

## Архитектура

```
producer.py ──▶ [sales.raw] ──▶ etl_consumer.py ──▶ [sales.clean]  (очищенные записи)
                                      │
                                      ├─▶ [sales.dead]  (DLQ: не прошли валидацию)
                                      └─▶ [sales.mart]  ──▶ sink.py ──▶ SQLite mart.db
```

Топики:

| Топик | Что внутри | Ключ сообщения |
|---|---|---|
| `sales.raw` | сырые JSON-события продаж | `order_id` |
| `sales.clean` | очищенные и обогащённые записи | `order_id` |
| `sales.mart` | агрегаты: выручка по категории за минутное окно | `category` |
| `sales.dead` | события, не прошедшие валидацию, с причиной | `order_id` |

## Проверенный прогон

- 23 сырых события продюсера
- 15 очищено и обогащено сегментом клиента
- 3 дубля отброшены по `order_id` (дубликаты с ts не новее сохранённого)
- 5 событий ушли в DLQ с причинами: `missing:...`, `bad_amount`, `bad_quantity`
- 11 записей витрины; например, окно 10:00:00, «Техника»: выручка 8140.50,
  2 заказа, 3 товара (refunded в выручку не попадает)
- sink загрузил 11 строк в SQLite

## Как устроено

- `config.py` — адрес брокера, топики, параметры окна (60 сек, допуск на опоздания 10 сек).
- `broker.py` — абстракция брокера: `KafkaBroker` (kafka-python) и `FakeBroker`
  (in-memory). ETL-код не знает, на чём работает, — поэтому тестируется без инфраструктуры.
- `transform.py` — чистые функции: парсинг `'1 250,50 руб.'` → `1250.5`,
  ISO-дат, нормализация категорий и статусов, валидация. Именно этот слой покрыт тестами.
- `producer.py` — синтетический поток с намеренной «грязью»: дубликаты, битые суммы,
  нулевые/отрицательные количества, пропущенные поля.
- `etl_consumer.py` — класс `Pipeline` (состояние стрим-процессора) + функция `run`:
  дедупликация, обогащение, tumbling-окна с watermark (закрываем окно, когда
  `max_ts − 10 сек` перешагнуло его конец), публикация в `sales.clean`,
  `sales.mart` и DLQ.
- `sink.py` — идемпотентная запись витрины в SQLite (`INSERT OR REPLACE` по ключу
  `(category, window_start)` — повторный прогон не плодит дубли).

## Сознательные упрощения (и что бы поменять в продакшене)

- Состояние дедупликации и окон живёт в памяти процесса. В проде — Kafka Streams
  (RocksDB state store) или checkpoint состояния, иначе рестарт консьюмера теряет счётчики.
- JSON вместо Avro/Protobuf: добавил бы Schema Registry и контракты схем.
- Семантика at-least-once. Для exactly-once — идемпотентный продюсер + транзакции.
- Топики создаются автоматически, без партиций и репликации: в проде — партиции
  по `order_id`, replication factor 3, грамотный `retention`.
- Обогащение справочником из файла: в проде — compacted-топик с изменениями
  справочника и KTable в Kafka Streams.

## Развитие проекта

- Заменить ручные окна на Kafka Streams (Java) или Faust (Python).
- Метрики: consumer lag, скорость обработки, размер DLQ — экспорт в Prometheus.
- CI через GitHub Actions: линтер + тесты на каждый пуш.
